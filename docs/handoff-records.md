## Handoff to mixo-geocore: three more item kinds — dental model, night guard, retainer

*Was `docs/handoff/geocore-item-kinds.md`.*

**For:** `mixocreative/mixo-geocore` (vendored here at engine 63, commit `b5a71ab`).
**From:** mixoDental, 2026-11-11.
**Why:** the owner needs the app to offer **dental model**, **night guard** and **retainer** as item
types. The host cannot add any of them, and the three are not the same size of ask.

### Why the host cannot do this alone

```ts
// vendor/mixo-geocore/host/dental/dentalKind.ts
export type DentalKind = 'aligner' | 'denture';
```

A kind is not a label. It selects a **profile family** (`ALIGNER_PROFILES` / `DENTURE_PROFILES`) and,
behind it, a pipeline. And the profiles themselves are generated:

```ts
// host/dental/profileFiles.ts
// Generated by scripts/gen-profile-files.mjs from
// crates/geometry-core/src/dental/profiles/*.json: do not edit.
```

`crates/` is not vendored here — only `host/` and the built packages — so **neither a new kind nor a new
profile can be added from this repo.** The host's part is small and known: 13 files branch on the kind.

### The ask, in three parts of very different size

#### 1. Night guard — probably one profile file

`alignerProfiles.ts` says it outright: *"Adding an aligner type is adding one file there: this list, the
card, the operator defaults and limits all follow, with no code change."*

A night guard is what an aligner is, mechanically: a thin shell, supported along its lower rim. It is
**thicker and unsegmented**, so it wants different numbers, not a different pipeline.

**What we need:** one `crates/geometry-core/src/dental/profiles/night-guard.json`, same schema as
`reference-aligner.json`, with values chosen by someone who knows the material. We deliberately have not
guessed: `ProfileDefaults` has eighteen fields — `outerSpacingMm`, `innerSpacingMm`, `maxSearchMm`,
`overhangAngleDeg`, `minTipSeparationMm` and the rest — and inventing a set would be fiction dressed as
data.

**Open question for you:** does a night guard's extra thickness change the rim detector's behaviour, or
only the support numbers? If the former, this is not just a profile.

#### 2. Retainer — one profile, and one real question

Also a thin shell, so the same shape of answer. But a retainer has **a wire across the opening**, and
that is geometry the aligner pipeline has never met.

**The question we cannot answer from here:** what does rim detection do with the wire?

- Does the wire join the two sides into one loop, so the detected rim runs round the wire instead of the
  shell's trim edge?
- Do the clasps count as part of the shell?
- Should the wire be excluded from the support area, or does it need support of its own?

If the answer is "detection needs to know about the wire", this is a pipeline change, not a profile.
**Please answer this before quoting the work**, because it decides which of the two it is.

#### 3. Dental model — a new kind, like `denture`

This one is genuinely different, and the reference sheet's own caption says why:
*"Solid · stable base / Low · base supports."*

- It is **not a shell**. There is no trim edge, so there is no rim to detect or draw.
- There is no "support area along each edge": supports go **under a flat base**.
- The whole Step 1 / Step 2 flow — rim, then the band along it — does not apply.

So it wants its own profile family and its own pipeline, exactly as `denture` has. That precedent is what
makes this a known quantity rather than research: `dentureProfiles.ts`, `DENTURE_PROFILES`,
`defaultProfileId`, `kindOfProfile` and `requireKind` already show the shape a third family takes.

**What we need:**
- `DentalKind` gains `'dental-model'`, and `DENTAL_KINDS`, `isDentalKind`, `defaultProfileId`,
  `profileIdsOf`, `kindOfProfile` and `requireKind` all follow.
- A `MODEL_PROFILES` family with at least one reference profile.
- A support strategy for a solid object on a base. Whether that reuses the denture path or needs its own
  is your call, not ours.

### What the host already has

The three icons are drawn and sitting unused, so nothing waits on art:
`src/ui/assets/art/dental-model.svg`, `retainer.svg`, `night-guard.svg`. The style book marks all three
**drawn, not wired up yet** so nobody draws a second set. `src/ui/iconCatalogue.ts` lists them.

### What we are NOT asking for

Not the other six kinds on the owner's reference sheet (surgical guide, crown & bridge, custom abutment,
wax-up, gingiva mask, bracket transfer tray, impression tray). They are drawn nowhere and wanted by
nobody yet. **An icon for a kind the pipeline cannot build is a promise the app does not keep**, and the
same goes for a profile nobody asked for.

## Handoff to mixo-geocore: orient and scan print angles from a rim the operator DREW

*Was `docs/handoff/geocore-orient-from-drawn-rim.md`.*

**For:** `mixocreative/mixo-geocore` (vendored here at engine 63, `b5a71ab`).
**From:** mixoDental, 2026-11-10. Companion to `geocore-region-from-drawn-rim.md`; follows
`geocore-rim-from-points.md` (delivered, engine 61).
**Why now:** the owner asked whether auto-orientation can be derived once the operator has drawn the
rim. It can — the maths is already in the engine — but not from the browser build, and not with the
scan that needs it.

### The gap, stated as the operator meets it

Detection that fails takes the operator into rim define mode. They draw the rim, press Done, and the
aligner goes to Step 2 **at whatever orientation the file happened to arrive in**. No print-angle
scan, no dial, no "Auto orientation" — all of which a detected aligner gets. The host cannot offer
them, because every entry point that would produce them re-runs the detection that already failed.

Measured on this engine (`pkg-node`, engine 63, a shape with no findable trim):

| Call | Result |
|---|---|
| `orient_dental` | `failed`, reason `no-trim` |
| `dental_tilt_scan` | `failed`, reason `orientation-no-trim` |
| `propose_dental_region` | `inconclusive`, reason `orientation-no-trim` |

`scanDentalTilts` takes mesh + profile + support settings and no rim
(`host/dental/dentalTilt.ts:120-124`), so there is no way to hand it the rim the operator just drew.

### What already exists, and is the reason this is a small ask

`dental_pose(positions, indices, rim_scalars, profile)` is declared in
`pkg-node/mixo_geometry_wasm.d.ts` and **absent from `pkg-browser`**; the host treats it as test-ABI
only (`host/dental/dentalEngine.ts:288-295`, `host/dental/dental.ts:76-83`).

Probed on the reference aligner, pre-rotated by an arbitrary Euler: feeding its own detected loop
through `dental_rim_from_points` and then `dental_pose` returns a rotation **5.60 degrees** from
`orient_dental`'s. That is the same figure `geocore-rim-from-points.md` records for the axis, and it
is the expected difference — detection uses the shell's least-variance axis, a drawn rim uses the
plane of the loop.

Two findings that shape the asks:

- On an ambiguous arch, `dental_rim_from_points` succeeded and `dental_pose` returned **empty**. So a
  pose from a rim can legitimately say "don't know", and the host must keep manual orientation as the
  fallback. Please give a stable reason code rather than an empty return alone.
- The scan's own pick sat **10 degrees** from `orient_dental`'s rotation (start 46.46, pick 36.46).
  A pose is only the scan's starting point, so ask 2 matters more than ask 1.

### The asks

**1. Pose on the drawn-rim result.** Add `rotation(): Float64Array` to `DentalRimResult`, mirroring
`DentalOrientResult.rotation()` (Euler XYZ, empty when ambiguous, with a reason code) — or promote
`dental_pose` to the production session ABI.

> This **reverses point 5 of `geocore-rim-from-points.md`**, which says `front` must be absent because
> "this flow switches auto-orientation off entirely". That was the owner's 2026-11-05 decision, taken
> when a drawn rim could not produce a frame. The owner reopened it on 2026-11-10.

**Open question we could not test:** the only profile here is a `ring` arch, where the reference works
with `front` absent. An open (non-ring) arch presumably needs a `front` — does the engine derive it
from the loop's U parameter, or does it want a hint from the host?

**2. Scan the print angles from a given rim.**

```
dental_tilt_scan_from_rim(model, points, flip, profile,
                          neck_length_mm, pillar_diameter_mm, lift_mm, braced, on_tilt?)
    -> DentalTiltScanResult
```

Same `points` as `dental_rim_from_points`, and the same result type, so the host reuses
`decodeTiltScan` unchanged.

**Open question:** the scan's rules (`rim-gap`, fitting-side tip counts) look as though they need a
region internally. If so this depends on ask 3. We have no Rust source vendored and cannot check.

**3. `dental_region_from_rim`** — already asked for in `geocore-region-from-drawn-rim.md`. It becomes
a prerequisite here too, because the print-angle confirm only accepts a two-contour policy
(`src/dental/confirmTilt.ts`).

### How the host will know these landed

`src/vendorCapabilities.test.ts` watches for each symbol and **fails when it appears**, carrying the
undo list in the message. A workaround that keeps passing is exactly how a delivered capability goes
unnoticed, so the check is inverted on purpose.

### What the host does until then

Nothing is stubbed and no seam is built for this — the watch announces arrival, and a placeholder
would be code with no caller. The honest interim behaviour is already in place: a drawn-rim aligner
goes to Step 2 at its drop orientation, and the controls that cannot act are shown-and-disabled with
the reason beside them rather than live-and-inert.

**Proof to run when they land:** a `u5`-style walk on a shape with no findable rim — draw, Done, and
Step 1 must show the tilt dial with a pick and an Auto orientation button, instead of asking the
operator to turn the aligner by hand.

## Handoff to mixo-geocore: propose a support region from a rim the operator DREW

*Was `docs/handoff/geocore-region-from-drawn-rim.md`.*

**For:** `mixocreative/mixo-geocore` (vendored here at engine 63, `b5a71ab`).
**From:** mixoDental, 2026-11-09. Follows `geocore-rim-from-points.md` (delivered, engine 61).
**Why now:** the owner approved letting a DETECTED rim be redrawn by hand (2026-11-09), and that
turned a latent gap into one the operator meets in the first five minutes.

### The gap, stated as the operator meets it

Step 2 has three sliders on `DentalTuning` — **Area width** (`stripWidthMm`), **Area position**
(`positionMm`, "higher moves the support area farther onto the outer surface; lower moves it toward
and across the edge") and **Support density**. They are the right controls and they work.

They work **only for a detected rim**. `useDentalTuning` reads tuning from a `two-contour` policy and
returns early for anything else; a hand-drawn rim lands a `manualAreaPolicy` instead —
`kind: 'legacy'`, `origin: 'manual-area'`, carrying whatever stamps the operator had — because, in
`useRimDrawing.onRimDone`'s own words, *"the rim is the operator's, and there is no detected area to go
with it."* So Step 2 opens empty to be painted.

**AND IT IS WIDER THAN A DRAWN RIM, which is worth knowing before costing this.** The same
`manualAreaPolicy` is set when detection finds a rim but **no area** (`useDentalFlow`), and that is
the more common route by far. Both reach the same dead end.

**The host will know the day this lands, without anyone remembering to look.**
`src/vendorCapabilities.test.ts` watches the vendored engine's TypeScript surface for
`dental_region_from_rim` and FAILS when it appears - an inverted check, because a workaround that
keeps passing is exactly how a delivered capability goes unnoticed. The failure message carries the
undo list, so the bump that turns it red is good news with instructions attached.

**What the host did in the meantime (`bcf8583`, 2026-11-09), so this is not read as still broken.**
The three sliders used to render, move and steer nothing — the operator dragged one, the thumb sprang
back and nothing was said. They are now **shown-and-disabled** with the reason on screen ("This area
is painted, so change it with Paint and Erase"), which is the house rule for a control with nothing to
act on. That is honest, not fixed: the operator still cannot size a band around a rim they drew, and
the host cannot give them one, because nothing proposes a region from a given rim. **Landing the entry
point below is what makes those three sliders live for a hand-drawn rim and for every aligner whose
area was never detected** — `useDentalTuning.tunable` is the single host-side switch that flips.

### Why the host cannot do it

- `propose_dental_region` **re-detects** the rim; it does not take one.
- `dental_rim_from_points` (engine 61) returns the plane, the side and the 96×96 visibility mask —
  and deliberately nothing else. `geocore-rim-from-points.md` records the reason the mask is the
  engine's and not the host's: *"a blank mask permits nothing at all (painting stops working), a full
  one permits supports where the opening cannot reach"*, and a TypeScript raster would be a second
  source of truth tracking the Rust one through every engine bump with no test that could prove they
  agree. Every word of that applies here, and more strongly: a region is what decides where supports
  are allowed to land.

### The ask

One call, the region counterpart of `dental_rim_from_points`:

```
dental_region_from_rim(model, points, flip, profile, tuning) -> DentalRegionResult
```

- `points` — the same dense curve the host already resamples for `dental_rim_from_points`
  (`RIM_SAMPLE_SPACING_MM = 0.5`), so the two calls take the same input and cannot disagree about
  which rim they were given.
- `tuning` — `stripWidthMm`, `positionMm`, `density`, exactly the three the sliders already own.
- Result — whatever `propose_dental_region` returns for a detected rim, so the host can store a
  `two-contour` policy and every consumer downstream is unchanged.

Taking the rim's own plane (the one `dental_rim_from_points` fitted) rather than re-deriving it is
the point: the operator drew that loop, and the band has to hang off what they drew.

### What the host will do with it

`useRimDrawing.onRimDone` stops storing `manualAreaPolicy` and stores the `two-contour` policy this
call makes possible, with the profile's default tuning. From there nothing else changes: the sliders
already read `policy.tuning`, `useDentalTuning`'s retune path already exists, and Step 2 stops opening
empty for a rim the operator took the trouble to draw.

**Until it lands**, the honest host-side behaviour is the one shipping today — Step 2 opens empty and
is painted by hand — and the two sliders should arguably be hidden rather than shown inert for a
drawn rim. That is a host decision and is recorded as debt in `docs/HANDOFF.md`, not done here,
because hiding a control the operator has learned to look for deserves the owner's say.

### How to prove it

`npm run walk -- --only=u` in mixoDental against the new vendor drop: redraw the rim on the reference
aligner (`u9b` already gets there), press Done, and Step 2 must open with a band rather than empty,
with Area width moving it. The check to add is the mirror of `u10c`, which already proves exactly that
for a detected rim — *"Area width widens the area and moves the tip preview onto its middle line"*.

## Handoff to mixo-geocore: build a `DentalRim` from operator-drawn points

*Was `docs/handoff/geocore-rim-from-points.md`.*

> **DELIVERED, 2026-11-06 — geocore engine 61, commit `8bd2430`.** This ask is answered and the host is
> wired to it (`src/dental/rim/drawnRim.ts`). Kept as the record of what was asked and why.
>
> **What came back differed from this document in two ways, both measured rather than argued:**
> 1. **The opening sign** is decided by `orient::floor_offset`, the measure detection already uses —
>    not by the two-way centroid raycast suggested here, which barely separates through a thin shell.
>    Below the profile's threshold the engine returns `rim-side-uncertain` and leaves the flip to the host.
> 2. **A drawn rim does not reproduce a detected one.** Feeding the reference aligner's own detected
>    loop back gives an axis **5.60°** from detection's, because detection's axis is the shell's
>    least-variance axis, not the plane of the loop it traced. The side agrees; the axis does not, and
>    cannot. Masks 5104 cells against 5089, agreeing in 8919 of 9216 — all pinned in the engine's test.
>
> The delivered signature is
> `dental_rim_from_points(model, points, flip, profile) -> DentalRimResult`, and the complete
> `reason()` set the host branches on is `"rim-collinear"` (failure) and `"rim-side-uncertain"`
> (success, side undecided). `"rim-too-few-points"` exists in the Rust enum but is unreachable through
> the ABI; everything else throws.


**For:** `mixocreative/mixo-geocore` (vendored here at engine 60, commit `d2754369`).
**From:** mixoDental, 2026-11-05. Design: `docs/design/2026-11-05-rim-define-mode.md`.
**Why:** mixoDental is adding a mode where the operator draws the rim by hand when detection cannot find
one. The host can do all of it except the one part only the engine can do.

### The ask

One call. Same shape as an orientation result's rim, built from points the operator drew instead of from
detection:

```
dental_rim_from_points(
  positions: Float32Array,   // unit-local mesh, as every other dental call takes it
  indices: Uint32Array,
  anchors: Float64Array,     // the operator's ordered anchor points, xyz each, unit-local, ON the surface
  openingHint: Float64Array, // xyz unit vector: which side the operator says the opening faces (see below)
  profile: string,           // aligner profile id, for the same thresholds detection uses
) -> DentalRimFromPointsResult
```

Result, mirroring `DentalOrientResultLike` so the host decoder is the one it already has
(`host/dental/dentalEngine.ts:310` `rimScalars` / `:321` `rimOf`):

```
status(): number            // 0 built, 1 refused
reason(): string            // a stable CODE, not prose - see "Reasons" below
rim_scalars(): Float64Array // the existing 22-number layout, unchanged
take_rim_points(): Float32Array
take_visibility_mask(): Uint8Array
free(): void
```

### The input is a general surface loop, not an aligner thing

Worth saying because it may shape where you put this. On the mixoDental side the drawing is **not** a dental
feature: a closed run of points on a model's surface is a general capability (`src/core/surfacePath/`,
portable and engine-free), and the same list with the join removed is an open path reused elsewhere. The
dental rim is its first consumer.

So `anchors` is just an ordered loop of surface points. If geocore would rather expose the general shape —
"fit a frame and rasterise a visibility mask for this loop on this mesh" — with `DentalRim` assembled from
it on the dental side, that suits this caller equally well and would serve a denture or a future aligner
type without a second call. The dental-specific parts are only `profile` and the `DentalRim` packaging.

### What the host sends, and guarantees

- **`anchors` are already on the surface.** Each one is a raycast hit against this same mesh
  (`src/components/viewport/rustRaycast.ts`, i.e. the engine's own `session.pick`), converted to unit-local.
  The host does not send points floating in space. If a tolerance check is wanted anyway, refuse rather
  than snap silently.
- **Ordered, and closed implicitly.** Anchor *n* joins anchor *0*. The last point is not a repeat of the
  first, matching `DentalRim.points`' own rule.
- **At least 3**, validated host-side first; the refusal is here as a backstop.
- The host has already refused a loop that self-intersects when projected into its own plane, has a
  degenerate enclosed area, or whose anchors are collinear — `src/core/surfacePath/validate.ts`, with the
  same codes this document asks for. Again: backstop, not primary.

  One warning from writing that validator, in case the engine does the same checks: do **not** fit the
  loop's plane with Newell's method. It sums signed areas, so a self-crossing loop cancels — a symmetric
  bowtie gives an exactly zero normal, and the loop then looks collinear rather than self-crossing. Fit the
  plane from the anchors furthest apart and measure the area separately in it.

### What only the engine can do, and why this call exists

`DentalRim.visibilityMask` is a 96 × 96 orthographic raster of projected mesh depth in the rim frame. The
host cannot produce it:

- Nothing in the binding surface builds a mask. Across `GeometrySession`, `DentalEngine` and
  `DentalInternals` it only ever comes *out* of orientation, via `take_visibility_mask()`
  (`dentalEngine.ts:22`). There is no `mask_from_rim(mesh, frame)`.
- It is **not optional**, and not ignorable even for a hand-painted area. Measured on the shipped reference
  aligner, calling `dental_allowed_vertices` with one allow stamp and varying only the mask:

  | `manualArea` | mask | allowed vertices (of 186 976) |
  | --- | --- | --- |
  | true | the real mask | **1804** |
  | true | all zero | **0** |
  | true | all one | **2018** |
  | either | zero-length | throws `INVALID_LENGTH` |

  So a blank mask is a silent dead end — the operator paints and nothing is ever permitted, with no error —
  and an all-ones mask admits supports where the cavity opening cannot reach, which is a print-safety
  fault.

A TypeScript reimplementation of that raster was considered and rejected: it would be a second source of
truth for a safety-relevant mask, needing to track the Rust rasteriser through every engine bump, with no
test able to prove agreement beyond the fixtures that happen to exist.

### What the engine should do with the anchors

1. **Densify along the surface** between consecutive anchors, so `take_rim_points()` returns a dense loop
   comparable to a detected one (the reference aligner's detected rim has 158 points). The engine has the
   mesh and the raycaster; doing it here keeps one definition of "the curve follows the model". If the
   engine would rather receive the dense loop, say so and the host will send it instead — but then the two
   repos each own half of the curve, which is worse.
2. **Compute the frame** — `centroid`, `openingDirection`, `tangent`, `bitangent` — from the loop, the same
   way detection does once it has a boundary.
3. **Rasterise the visibility mask** with the existing code path, and fill `visibilityResolution`,
   `visibilityMin`, `visibilityMax` to match.
4. **`boundaryKind` must come back as `projection-fallback`** (scalar 0 = `1`). A hand-drawn rim has not
   earned `lower-edge-loop`, which certifies two sharp terminal loops were found. `projection-fallback` is
   already what the shipped reference aligner's own rim reports, so it is not a lesser class in practice.
   If a distinct third kind (`operator-defined`) is wanted so consumers can tell them apart, that is a
   `DentalRim` type change and a separate decision — say which you prefer.
5. **`front` must be absent.** It exists for pose estimation, and this flow switches auto-orientation off
   entirely: a self-defined rim means no re-detection and no print-angle scan.

   > **SUPERSEDED, 2026-11-10.** The owner reversed the decision this rests on. "Auto-orientation off
   > entirely" was right when a drawn rim could not produce a frame; engine 61 made it one, and a probe
   > on this engine shows `dental_rim_from_points` + `dental_pose` returning a rotation 5.60 degrees
   > from `orient_dental`'s on the reference aligner. What a drawn rim should get is the same dial and
   > scan a detected one gets. The asks are in
   > [`geocore-orient-from-drawn-rim.md`](#geocore-orient-from-drawn-rim), including the open
   > question this point raises: whether an OPEN (non-ring) arch needs a `front`, and whether the
   > engine derives it from the loop or wants a hint.

#### `openingHint`, and why the host sends it

A plane normal has two directions and only one points out through the opening. Deciding it from the drawn
winding would silently depend on which side the operator's camera happened to be on, so the host asks the
operator and shows the answer as a flippable arrow.

Treat `openingHint` as authoritative for the **sign** only: compute the plane normal, then flip it to the
hemisphere `openingHint` points into. Do not re-derive the side. If `openingHint` is not a finite unit
vector, refuse with `BAD_OPENING_HINT` rather than guessing.

### Reasons (stable codes, not prose)

Please return codes, not sentences. mixoDental ships in English, Japanese and Taiwan Chinese, and a Rust
sentence would be the only untranslated text in the app:

`TOO_FEW_POINTS`, `SELF_INTERSECTING`, `DEGENERATE_AREA`, `COLLINEAR`, `POINT_OFF_SURFACE`,
`BAD_OPENING_HINT`, `MASK_FAILED`.

This is the same ask as the one already outstanding for `orient_dental`'s own failure `reason()`, which
returns prose today and so cannot be shown to an operator in their language. Both would be fixed by the
same convention.

### How to verify it

The reference aligner makes this checkable against ground truth, which is unusual and worth using:

1. Orient `docs/dental-reference/reference-aligner.stl` normally. Keep its detected rim — 158 points,
   `projection-fallback`, mask 5089 of 9216 bytes set, `visibilityResolution` 96.
2. Feed a subsample of those same rim points back in as `anchors`, with `openingHint` set to the detected
   `openingDirection`.
3. The returned frame should match the detected one closely, and the returned mask should match the
   detected mask closely. Exact equality is not expected from a subsampled boundary; a large divergence
   means the frame or the raster is being derived differently.
4. Then `dental_allowed_vertices` with one allow stamp should admit a count near the detected rim's **1804**
   — not 0, and not the 2018 an all-ones mask gives.

### What mixoDental does meanwhile

The mode is being built against this call. Until it exists, the mode's **Done** refuses with a plain
sentence rather than pretending: the operator can draw, adjust, close and validate a rim, and the handover
to Free transform is blocked at the last step. Nothing ships a blank or full mask as a stand-in.

## Handoff to mixo-geocore: spatial input as a second device, beside the pointer

*Was `docs/handoff/geocore-spatial-input.md`.*

**For:** `mixocreative/mixo-geocore` (vendored here at engine 63, commit `b5a71ab`).
**From:** mixoDental, 2026-11-11.
**Why:** the owner's call — the puck's commands belong in the engine so mixoMesh and mixoDental do
not each write them. This doc says which part of the puck belongs there and which part must not,
and why the line falls where it does.

### The owner is right, and geocore already set the pattern

`editing/ViewportPort.ts` opens with the rule:

> The only way `editing/` reaches a 3D view (D22). Each app implements it over its own renderer
> (Babylon in mixomesh, three.js in mixoDental); everything drawn (rings, ghost tips, overlays,
> highlights) stays in the app. Editing code works in plain data.

That is exactly the shape this needs, with the device in the renderer's place. geocore owns **what a
turn means**; the app owns **the device that turned**. `editing/` is already the shared interaction
layer and not a geometry library — it holds `gesture.ts`, `keys.ts`, `modes.ts`, `numberInput.ts`,
`pick.ts`, `dragOver.ts` and a typed command registry — and mixoMesh vendors exactly `editing/` and
`host/`, importing them from `EditBar.tsx`, `sessionStore.ts` and `supportData.ts`. So the sharing is
demonstrated, not hypothetical.

### What geocore does not have, which is the core of the ask

```ts
// host/core/vec3.ts
export type Vector = [number, number, number];     // and nothing else — there is no quaternion
```

```ts
// host/core/transform.ts
/** … rotation as Euler angles in radians, order 'XYZ' (world frame Y up, right-handed).
 *  The matrix is `T · R`, R = Rx · Ry · Rz. */
export interface Placement { position: Vector; rotation: Vector }
```

The puck sends a **unit quaternion**; the engine's rigid placement is **Euler XYZ in radians**. So a
quaternion-to-`Placement` conversion has to exist, and it is precisely the thing that must exist
**once**. Written twice it will differ, and the symptom is *"the model turns the wrong way about one
axis only"* — which reads like a sign error and is not one.

### The three layers, and where each belongs

| Layer | What it is | Home | Why there |
|---|---|---|---|
| **transport** | `navigator.bluetooth`, GATT, reconnect, the chooser's user gesture | **mixospatial** `web/src/puck.ts` | browser I/O. geocore has a *port* for the renderer and never touches three.js or Babylon; the symmetric rule is a port for the device and no `navigator.bluetooth` in the engine |
| **codec** | bytes → quaternion; the version rule; reject-and-surface | **mixospatial**, beside the firmware | if the packet layout changes, firmware + codec + fixtures change in **one commit in one repo**. Split them and `protocol/fixtures/` stops being a single source of truth, which is the whole reason it exists |
| **the command** | quaternion → `Placement`; re-zero; what "turn the model" *means*; the labels and the enabled state | **geocore** `host/core/` + `editing/` | both apps need the same answer and must not each derive it. This is the sharing the owner asked for |

**The transport is genuinely not the same in the two apps**, which is the strongest argument for the
line being here rather than one layer up: mixoDental is a browser tab, where Web Bluetooth is
Chromium-only and `requestDevice()` must be called from a click handler. mixoMesh is Electron 43,
where Web Bluetooth needs a `select-bluetooth-device` handler in the main process. Two transports,
one command — the same situation as Babylon against three.js, answered the same way.

### The ask, in three parts of very different size

#### 1. A quaternion in `host/core` — small, pure, and the only part with maths in it

`host/core/quat.ts`: a `Quat` type, `multiply`, `conjugate`, `normalize`, `fromAxisAngle`, and
`toPlacementRotation(q): Vector` — the quaternion expressed in the Euler convention
`transform.ts` already documents. No WASM, no `crates/` change, testable in the existing suite.

**The trap, written here so it is met before it is made:** `transform.ts` documents
`R = Rx · Ry · Rz`. A quaternion-to-Euler conversion that assumes the ZYX order most references use
is wrong, and it is *correct at rest and for small tilts* — so it passes a smoke test and fails on
the first real turn.

Component order is a second one: the puck's wire format is `x, y, z, w` (`w` last, matching
three.js), recorded in `mixospatial/PROTOCOL.md` §5. Pick an order in `quat.ts`, say which, and make
the fixtures cross it.

#### 2. A device record and a port — mirroring `PointerRecord` and `ViewportPort`

`editing/SpatialPort.ts`, in plain data exactly as `PointerRecord` is:

```ts
export interface SpatialRecord {
  /** Unit quaternion, the app's own frame, w last. */
  quaternion: readonly [number, number, number, number];
  status: { still: boolean; uncalibrated: boolean; lowBattery: boolean };
  /** The device's own counter. A GAP means notifications were dropped. */
  seq: number;
  /** Milliseconds, any monotonic origin — as `PointerRecord.timeStamp`. */
  timeStamp: number;
}
```

geocore never sees a byte and never sees a GATT handle. **Carry `seq` through**: the puck's
`PROTOCOL.md` §8 requires that a discarded packet be *surfaced*, and `editing/status.ts` and
`editing/toast.ts` are where a count becomes something a person sees. A port that drops `seq` makes
that rule unimplementable in the layer that owns the words.

`status.uncalibrated` matters for the same reason: until the puck has a stored zero it reports a raw
frame, and the app has to say so rather than quietly show a plausible wrong orientation.

#### 3. Rows in the command registry — **CORRECTED 2026-11-12, and this part of the ask is withdrawn**

**What this section claimed, and why it was wrong.** It asked for `spatial.connect`,
`spatial.rezero` and `spatial.disconnect` in `COMMAND_IDS`, on the grounds that *"both apps get
label, hint, role, enabled-reason and i18n key in one place"*. Two independent reviews of the
three-repo plan took that apart, and both were right:

- **"Both apps" is false, and nothing planned makes it true.** mixoMesh imports **17** `editing/`
  modules — `regenerate`, `addTip`, `shapeEdit`, `session`, `check`, `removal`, `stroke`,
  `selection`, `islandProblems`, `omittedProblem`, `screenBrush`, `selectionHighlight`, `pick`,
  `gesture`, `types`, `ViewportPort` — and **not `commands.ts`**, nor `keys.ts`, `modes.ts`,
  `status.ts` or `toast.ts`. It has its own UI state (`src/panels/supports/supportUi.ts`) and its own
  status words (`src/supports/live/statusText.ts`). The registry has exactly ONE consumer. A
  re-vendor is not an adoption: shipping it 64 does not make it call `resolve()`.
- **The field is `disabledReason`, not "enabled-reason"** (`editing/commands.ts:101`). Someone
  grepping this document for the name I used finds nothing. A new row also owes **six** required
  members — `role, label, hint, visible, enabled, disabledReason` — not the four I listed.
- **The input column was understated.** I wrote "a 4-field record + `UiState` in". `UiState` is not
  one field: it is **27 required fields** (`commands.ts:36-83`), of which a spatial row would read
  one or two. The row looked narrow because I shortened its input.
- **There is already a documented way to do this without touching core**, which I never named:
  `ExtraCommandIds` (`commands.ts:29`), `registerCommands()` (`:378`, with clash detection and a
  remover for tests), `commandIds()` merging both (`:396`), and `commandOf` falling through (`:401`).
  `UiState`'s own comment at `:35` says *"an app mode adds (optional) fields by augmenting it"*.
- **And the capability check is the transport wearing a plain-data coat.** `spatial.connect` IS the
  chooser's user gesture, which this document's own layer table assigns to the app: in a browser it
  must fire inside a click handler for `requestDevice()`, in Electron it needs a
  `select-bluetooth-device` round trip through the main process. One row, two press shapes. Worse,
  in Electron the capability is always true, so a shared "no Web Bluetooth here" sentence is a
  reason that can never be correct there — and because `disabledReason` is defined exactly when a
  visible command is not enabled, a permanently-false capability would make `spatial.connect`
  permanently visible-and-disabled in every app that renders the registry. That is a visibility
  policy, which is an app decision.

**So: parts 1 and 2 of this ask stand. Part 3 is withdrawn.** `host/core/quat.ts` and
`editing/SpatialPort.ts` are jobs with narrow outputs and belong in geocore. The three command rows
and the capability fact stay in **mixoDental**, registered through `registerCommands()`, until and
unless mixoMesh adopts `commands.ts` — and that adoption is its own piece of work with its own cost,
which no plan has priced.

The capability check itself is still owed, and the audit's point stands: a control that exists
nowhere is what made a browser with no WebGL2 render a blank page (MIXO-04). It just belongs in the
app, beside the check that now lives in `src/main.tsx`.

### The one design question inside this, with a recommendation

**Does the puck turn the camera, or the selected object?**

Recommended: **the selected object, falling back to the camera when nothing is selected.** The
puck's gesture is pick-it-up-and-turn-it, and that is what a person does to an object in their hand,
not to a room. The fallback keeps it useful with an empty selection, which is the state the app opens
in. If it turns out to feel wrong on real hardware, it becomes a `spatial.drive` toggle — one more
registry row, not a redesign. The owner's call either way.

### What is deliberately not asked for

- **No BLE in geocore.** Not the transport, not reconnect, not permission handling.
- **No new WASM and no `crates/` change.** All three parts are TypeScript in `host/` and `editing/`.
- **Nothing yet.** The puck's three bench answers come first (`mixospatial/docs/decisions/`): the
  CR2032 under BLE load, whether the IMU's tap interrupt survives a hand-held puck, and the drift of
  raw orientation over minutes. A port designed around an interrupt that does not work on a
  hand-held device is a port designed twice. The value of this doc today is that the boundary is
  settled before either side is written.

### The constraint found while checking this: the two apps are 51 engine versions apart

**Both apps pin their copy properly.** An earlier revision of this doc claimed mixoMesh had no
stamp; that was wrong, and it is corrected here rather than quietly dropped so nobody re-derives it.
mixoMesh's layout simply differs — the engine must be served by Vite, so it sits in
`public/vendor/mixo-geocore/` with the stamp, while the TypeScript sits in
`vendor/mixo-geocore/{host,editing}`. Looking only at the latter is what produced the wrong claim.

| | stamp | engine | commit |
|---|---|---|---|
| mixoDental | `vendor/mixo-geocore/SOURCE.json`, 110 files hashed | **63** | `b5a71ab` |
| mixoMesh | `public/vendor/mixo-geocore/SOURCE.json`, 97 files hashed | **12** | `6cc5385` |

Both verify. `node scripts/vendor-geometry.mjs --check` in mixoMesh exits 0:
*"mixo-geocore engine 12 (6cc5385) verified in public/vendor/mixo-geocore and vendor/mixo-geocore."*

**What actually follows is a schedule, not a defect.** Of the 94 `host/` + `editing/` files the two
apps have in common, **20 differ**, and mixoDental carries 16 the other does not. So `editing/` is a
layer both apps *vendor*, not a layer both apps are *level on*.

For this ask that means: a new `editing/SpatialPort` lands in geocore at 63 or later. **mixoDental
picks it up on its next vendor; mixoMesh picks it up only when it re-vendors across 51 ABI
versions**, which is its own project and not a side effect of this one.

And the §3 correction above sharpens this rather than softening it: the gap is not the only reason
mixoMesh would not share the command rows — **it does not import the registry at all**, so levelling
the engine would not hand it those rows either. Write the port for geocore, expect mixoDental to be
its only consumer for now, and do not size the work as though both apps light up together.

The one cheerful part: because both stamps exist and both carry `engineVersion`, measuring that gap
is reading two files. No new mechanism is needed to see it — only the habit of looking.

## Handoff to mixo-geocore: a job stuck at 100 % must stop looking finished

*Was `docs/handoff/geocore-stuck-job-elapsed.md`.*

**For:** `mixocreative/mixo-geocore`, `host/workers/jobActivity.ts` (vendored here at engine 62,
`vendor/mixo-geocore/host/workers/jobActivity.ts:221`).
**From:** mixoDental, 2026-11-09. Found by fault injection: `npm run walk -- --only=r --probes=r4`,
G7 in `docs/reviews/2026-11-09-wiring-walk-dental-flow.md` §6b.
**Why it is here and not fixed in the host:** mixoDental consumes `host/` and `editing/` **as built**
and never edits them (`scripts/vendor-geometry.mjs`; every vendored file is hashed in `SOURCE.json`,
and `npm run vendor:check` fails on an edit). So this is written down rather than patched locally.

### What the injection did

The walk swallows every settling reply from the analysis worker (`window.__faultHold`), which is a
worker that finishes its work and whose answer never arrives — the shape of G7, a background job that
has stopped. A dental batch of two models was started and left for twenty seconds, far past the one
or two a row's orientation normally takes.

### What the operator saw

```
background work: ["Checking A r-cube · Aligner oriented 100% Cancel"]
deck rows:       ["Checking the orientation…", "Waiting its turn…"]
```

The deck rows are right: pending, and honestly pending. The **background-work row is not**. It reads
`Aligner oriented`, it shows a **full bar at 100 %**, and it will do so for as long as the job is
stuck. Nothing on it says how long it has been there. A job that has finished and a job that will
never finish draw the same row, which is the one thing the row exists to distinguish.

### Why the control that should catch this cannot fire

`JobActivity.view` already has the signal — and it is wired to the one state that does not need it:

```ts
showElapsed: state === 'indeterminate' && age >= LONG_JOB_MS,
```

A job only becomes `determinate` once it reports progress. So:

- a job that reports **no** progress and runs long → indeterminate → shows `{time} so far`. Good.
- a job that reports progress and then **stops** → determinate → never shows elapsed, and
  `remainingMs` is computed from the fraction, which is 1, so it has nothing to say either.

The second case is the one a stalled worker produces, and it is the one with no signal. This is a
control that is live, tested, and unable to fire for the failure it was written for.

### The ask

Make `showElapsed` depend on the job being STUCK rather than on it being indeterminate. The datum is
already recorded: `entry.firstProgress.at` and `entry.fraction` are kept, so a job's last movement is
known. Something of this shape, with the threshold geocore's own UX rules prefer:

```ts
// A determinate job that has not moved for this long is stuck, whatever fraction it stopped at.
showElapsed: age >= LONG_JOB_MS && (state === 'indeterminate' || now - lastProgressAt >= LONG_JOB_MS),
```

which needs one new field on the entry (`lastProgressAt`, set wherever `entry.fraction` is set).

**The secondary ask, if it is cheap:** a determinate bar should arguably not render 100 % until the
job settles — 100 % means done, and this job is not. Capping the drawn bar just under full until
`endedAt` is set would remove the stronger half of the wrong impression. The host has no opinion on
which of the two is the better fix; the measurable requirement is only that the two rows differ.

### What is NOT being asked

Nothing about cancellation: the row **does** offer Cancel (`AnalysisClient` passes a controller
signal, so `cancellable` is true), the operator is not trapped, and the walk asserts that the deck
stays usable throughout. This is about the row telling the truth, not about a way out.

### How to prove it fixed

`npm run walk -- --only=r --probes=r4` in mixoDental against the new vendor drop. The probe reads the
background-work rows while the detector is stopped; a fixed build shows an elapsed time on that row,
and `r4`'s check can then be tightened from "the deck still works" to "the stalled job says how long
it has been stalled".

## Walking the app from the deck — the rail, and the rim loop

*Was `docs/handoff/operator-walkthrough.md`.*

Written 2026-11-17, for the walk-through that got stuck twice: **how the four tools work**, and
**how a rim gets detected, edited or added**. Everything here is the code's own rule, with the file
that enforces it beside it, so a disagreement between this page and the screen means this page is

Walk it on `npm run dev` → <http://localhost:5173/mixodental/>. **Not the live site**: that is still

---

### 1. The rail is the order. There is no wizard.

Four tools down the left of the deck — **Orient · Rim · Area · Supports** — with the models beside
them. The dependency between them is shown by **what you can press**, not by marching you through
screens. Nothing is enforced beyond what is genuinely impossible.

`src/deck/toolState.ts` decides each tool's state and is pure: no React, no scene, no strings of its
own. `src/deck/ToolRail.tsx` decides how the states look.

#### The four states, in the order they are tested

The order **is** the rule: **unavailable → busy → stale → ready**, and all three pairs are
mutation-checked.

| state | what you see | what it means |
|---|---|---|
| **unavailable** | greyed, **with a line telling you what to do first** | the prerequisite is missing |
| **busy** | *not* greyed — it opens and shows progress | its own job is running right now |
| **stale** | still opens, marked | upstream changed; the work is still there but no longer matches |
| **ready** | pressable | nothing outstanding |

Two rules are the reason this is a module and not a condition inside a button:

1. **Greyed must say why, and what to do.** The type forbids an `unavailable` without its sentence,
   and a test asserts the three sentences differ — one generic line teaches nothing. A disabled
   control with no explanation is *worse* than a wizard step: you see grey and don't know the fix.
2. **"Not yet possible" and "being made right now" must not look alike.** Conflate them and you
   press a tool, see grey, and conclude something failed.

#### The lines you will actually hit

Each sentence belongs to the tool that **produces** the thing you're waiting on, whoever is waiting:

| waiting on | the line |
|---|---|
| Orient | *Turn the model the right way up first.* |
| Rim | *The area is measured from the rim, so draw the rim first.* |
| Area | *Mark the support area first.* |

**A tool waits for whatever is immediately above it in its own chain** — one rule, not four
constants. That matters because the chain is job-specific: a **denture** goes Orient → Supports, no
rim and no area, so its Supports waits on the *orientation*. Supports produces nothing, so nothing
ever waits on it; it is last in every chain.

#### Why re-orienting does not grey everything downstream

Because the work still exists. It says **stale** instead.

- One revision counter **per unit**, not per tool. (Per-tool, re-accepting Orient would score below
  the supports and nothing would ever go stale.)
- A tool is stale when its number is below **the newest revision anywhere above it in the chain**.
- **The rim and the area take one revision together**, because accepting the policy accepts both. A
  *detected* rim arrives inside that policy and never passes through `rim/set` at all.
- **A draft is not accepted work.** Drawing a rim stamps nothing — the rim is stamped when it is
  promoted into `unit.dental`.

The facts the rail reads come from the scene's own fields (`src/deck/unitFacts.ts`), never from the
revisions; revisions are used **only** for staleness. Read the facts from the revisions instead and
nothing on the rail opens until something has stamped one.

### 2. The rim loop: three ways in, one tool

This is the part that was confusing, and the confusion was in the code's history rather than in you
— **it used to have two tools whose meaning flipped on whether the loop was closed.** That is gone.

#### Three ways a rim comes to exist

| | how it happens | what you do |
|---|---|---|
| **detected** | detection finds the rim; it arrives inside the policy | nothing — it never passes through `rim/set` |
| **drawn** | detection finds none, so Step 1 detours to the `rim` stage | place handles, close the loop, Done |
| **redrawn** | you choose to redraw a rim that *was* detected | the loop is seeded from detection's own curve, then you edit it |

A redraw is seeded by `src/dental/rim/seedFromDetected.ts`: one handle every 12 mm of arc, plus one
wherever the rim turns 45°, capped at 48. **It is a replacement, not a lossless edit** — the axis
comes back about 5.6° different, and the command says so before you commit to it.

#### One tool, and what's under the press decides the act

`src/dental/rim/rimTarget.ts` is the whole grammar. It is pure — a path and a point in, a verdict
out — so every rule below is tested without a browser.

| what is under the press | what happens |
|---|---|
| a **handle** | pick it up and drag it |
| the **drawn line** | put a new handle in there, and pick *it* up |
| the **first handle**, loop open, 3+ points | close the loop |
| **bare model**, loop open | add a point at the end |
| **bare model**, loop closed | nothing to do here — so the press turns the view instead |

**Every press that lands something picks it up in the same press.** Append-and-drag,
insert-and-drag and grab-and-drag are one gesture, not two.

**The resolution order matters:** a handle always wins, because a press that nearly hits one must
become a drag of it rather than a new handle beside it. Closing is tested *before* grabbing on an
open loop, since the first handle is the closing target while the loop is open and only becomes
draggable once it is joined.

Three distances, and the middle one is the one that would otherwise bite:

| | mm | why |
|---|---|---|
| handle grab reach | 0.84 | how near a handle counts as grabbing it |
| line reach | 1 | a line is thinner to hit than a marker, and missing it only falls through to the camera |
| **insert clearance** | **2** | a press this near an existing handle **grabs it** instead of inserting a new one |

Without that last rule, a press that just misses a handle is still within reach of the line running
through it — so it would silently drop a new handle a fraction of a millimetre from the one you
meant to drag, and you would not see it until the shape went wrong. The reverse miss (an intended
insert becomes a drag) is visible as it happens and undone with one key.

#### Two traps that were found the hard way

- **The drawn line is the curve, not the chords.** It is sampled by the same `spanCurve` a press is
  measured against. Drawn as chords, the two disagreed by over a millimetre at the seeded spacing,
  and a press on the visible line did nothing.
- **A click that ends a drag is not a tap**, and it cannot be told from one by looking at the path.
  The browser fires `click` on every release, *before* React has rendered the drag's result — so the
  path the handler sees still has the dragged handle at its old spot, and the release point reads as
  bare surface. `rimTapAt` is that guard. Walk check `u5d` is how the gap was found.

#### What the pointer looks like

Rim define mode uses `cursor-rim.svg` (`src/components/viewport/style.ts`): a crosshair with a small
open square, and **the square's centre is where the point lands**. Off the model it is the `grab`
hand, because a drag there orbits. A CSS cursor never appears in a screenshot, which is why nobody
saw it until `npm run look` composited it — `.stitch/look/rim-cursor.png`.

Rim define mode shows **only what it owns**: anchors, the line between them, and the cursor. Support
Edit Mode's furniture used to be drawn here too — a ring the size of the erase reach and a cone
where a support would be added, in a mode whose only gesture is placing anchors. That was a dead
affordance and it was removed on 2026-11-17.

#### Done

`src/dental/rim/drawnRim.ts` resamples the loop along the surface, then calls
`dental_rim_from_points` (engine 61) for the plane, the side and the 96×96 visibility mask. **Our
own refusals are answered first, in our own words, before the engine is troubled.**

The drawing itself is scene state — `rimDraft` on the unit, set by `rim/set` and `rim/clear` in
`src/state/project.ts` — so the app's ordinary history undoes each edit, and **one drag is one undo
entry**.

### 0. The entry and the deck, rebuilt on your rulings (new — start here)

**Do:** look at the first screen, then drop **one** STL on it.

**Look for:**
- **A drop target, drawn.** The page is named `drop` and never used the word: the whole section was
  the target, announced by a 1px outline that only appears once you are already dragging.
- **"Or tell us what you are making"** under it, then the three keys. Two ways in, not two flows —
  answering first only **preselects** the category of the files you then pick.
- **One file lands on the DECK.** It used to skip the question entirely and assume *Aligner*, so a
  dropped denture went into the aligner flow and was told to draw a rim. One fork, four defects.
- **Nothing is offered before you name it** — no rail, no Start. The detector takes the category as
  an argument, so anything offered earlier would run on a guess. **Arrange is not gated**: moving
  objects so none overlaps is pure geometry.

**Do:** drop **eight** STLs.

**Look for:**
- **Rows at once, no question in the way.** The category is on each ROW, because a category and a
  type belong to a model and one drop can hold several kinds. **`Set all to`** at the end of the
  header is the one press that names a whole stage case; the footer counts what is still unnamed.
- **One line per file, about 28px.** It was a three-line grid measuring **109px** — 2,600px of
  scrolling for a stage case. A sound mesh now says nothing at all; the tally counts the ones that
  are not. Health is a warning mark, the orientation result a two-word chip — **hover either for the
  full sentence**, which is also what the rail states for the row you are on.
- **Back is in the deck's own header**, beside the heading. It was `position: absolute` to the
  window — written for the start screens, which have nothing above them — so it sat on the logo.
- **The page is 1100px wide**, not 560. A worklist is a table.
- **Remove is quiet until you reach for it.** Twenty-four red blocks were the loudest thing on a
  screen whose job is to show which rows need a person.
- **No type dropdown appears.** Each family ships exactly one profile, so it would be a question with
  a single answer — the reason the old Type screen was deleted. It appears by itself when a second
  profile file lands.

### 1. The badge, and the cursors (fixed)

### 2. The way out of the flow (changed, and this is the one to argue with)

**Do:** look at the header while in a step.

**Look for:**
- **"Use as any model"** where *Exit* used to be. The word Exit promised navigation; the press
  removes the model's supports, hand edits and dental settings. The capability is right and stays —
  it is the only route from a dental-started model to free work on the bench — only the name was
  wrong. It binds to *Any model*, the first screen's third purpose, so the app has one name for the
  idea.
- **Press it on a model with supports built.** It asks first, naming what goes. On a fresh model at
  Step 1 it does not ask, because the cost is a redetect and a prompt there teaches you to dismiss
  prompts unread.
- **Press Escape** in a step. It goes **back one level** — out of rim mode keeping the drawing, out
  of a step to the one before, out of Step 1 to the case. Its last rung used to be the destructive
  command, so the last Escape of a sequence destroyed work.

### 3. The case screen (most of tonight's work)

**Do:** drop **three or more** STLs, then press `Set all to` → Aligner.

**Look for:**
- **Arrange** and **Each object with model** in the footer. A case can now be finished without ever
  visiting the bench — previously those lived only there, and the bench is not rendered while a
  start screen is up. Export is off, **with its reason**, until something has supports.
- **"3 need you"** in red, and **"Checking 2 of 3"** while the robot runs. Rows that only wait say
  nothing: twenty-three lines of "Waiting its turn…" said how little was happening, not how far along
  it was. **Before a row is named it says nothing about detection at all** — it used to claim to be
  "waiting its turn" in a queue that cannot exist until the category is chosen.
- **Rows that need you sort to the top.** The rest keep the order you dropped them in.
- **The rail and the footer stay put** as the list scrolls.
- **Pick a finished row and press Start.** It opens *that* row. It used to open a different one
  silently, and once every row was finished the key vanished — which is the state a case ends in.
- **Press Escape.** It goes back to the drop page. On the deck it previously reached no handler at
  all: nothing focused the page on arrival.
- **Your files** in the header, from anywhere. It was gated to Step 1 for a day as scaffolding; the
  re-entry bug under it is fixed, so the gate is off.

### 4. The art pipeline (new command)

**Do:** edit any drawing in `src/ui/assets/art/` in Illustrator, export over it, then:

```bash
npm run art
```

It flattens polygons and rotated rects onto the 48×48 grid the folder promises, and **refuses to
write unless the result paints exactly the same cells**. `npm run art -- --check` says what would
change without writing. Edit however you like; run this after.

### (h) Redesign the tilt dial: DONE (P7d), tweak by tokens

The dial (`src/ui/parts/TiltDial.tsx`, in aligner Step 1 and denture Step 1) is a knob with a pointer at the angle, 25 ticks over the 240-degree arc (the ticks inside the stable range in the accent colour), the range ends as small labels at both arc ends, and the angle itself as a large number in the middle of the knob (P7e; the separate big number that stood under the badge is gone, since it said the same thing twice). In the app's instrument theme the knob is flat indigo and the pointer a white triangle; the paper set keeps the soft raised knob and its recessed dot. The "Stable a–b°" line is unchanged; so are drag, the arrow keys, `aria`, snapping, Auto orientation, Restore and the live tilt.

It is plain HTML + CSS (no SVG): each tick is a `<span>`, the knob a `<div>` with a `box-shadow`. What a designer tweaks, all in `src/styles.css` and listed in `docs/ui-styling.md` ("Print-angle dial"):

- `--dial-size` (168px): the one size; knob, ticks, dot, labels and shadows follow it.
- Colours in `:root`: `--dial-face`, `--dial-face-shade` (the knob's gradient), `--dial-shadow-dark`, `--dial-shadow-light`, `--dial-tick`, `--dial-tick-on` (stable range), `--dial-dot`, `--dial-dot-shadow`, `--dial-label`.
- Proportions in the `.tilt-dial` rule, as fractions of `--dial-size`: `--dial-knob-size`, `--dial-tick-radius`, `--dial-tick-length`, `--dial-tick-width`, `--dial-dot-size`, `--dial-dot-radius`, `--dial-shadow-offset`, `--dial-shadow-blur`, `--dial-label-size`.
- The number of ticks is the `ticks` prop (default 25, one every 10 degrees of the arc).
- data-ui names: `tilt-dial`, `tilt-dial-ticks` (ticks `.tilt-dial-tick`, `.is-on` in range), `tilt-dial-knob`, `tilt-dial-dot`, `tilt-dial-value`, `tilt-dial-label-min`, `tilt-dial-label-max`.
- Keys: the dial is a real ARIA slider. Arrows step by `step`, Home and End jump to the ends. The rules are the pure `keyValue` in `tiltDialGeometry.ts`, tested there.
- Try changes on the catalogue page (`/mixodental/kit.html`), which shows the dial in and out of range, disabled and at two sizes.

Open for the owner: the shadows go against mixo-app-style's "no shadows" rule (the owner asked for this look); the arc stays 240 degrees (the reference is about 270) so the drag mapping is unchanged. `scripts/walk.mjs` checks f1 to f5 now drive the dial itself (`[data-ui="tilt-dial"]`, its `aria-valuemin`/`aria-valuemax`, and the lit `.tilt-dial-tick.is-on` run in place of the old `.range-band`); the slider they used to drive is gone.
