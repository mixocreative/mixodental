# Styling the UI, the CSS and the 3D colours

A guide for a designer. You can change every colour, size and font of the app without touching React or three.js code. Everything lives in three places: `src/styles/theme.css` (**the app's theme: the colours, type and geometry it actually wears**), `src/styles.css` (the set underneath, and every rule that lays a control out) and `src/ui/assets/icons/` (the icons).

## The rules

1. **No colour in code.** No `#hex`, `rgb()` or `rgba()` in any `.tsx` file or in a viewport / 3D source file. A colour is a CSS token (`--name`) in `src/styles.css`.
2. **No inline `style=` in TSX.** Style by class name in `src/styles.css`. The only exceptions are values computed from data at run time (a progress width, a brush circle size, the canvas cursor, an engine debug swatch); they are listed, each with its reason, in `src/ui/noColourLiterals.test.ts`.
3. **Every word is `t('English text')`.** The English text is the key; the Japanese and Traditional Chinese lines live in `src/locales/ja.ts` and `src/locales/zh-Hant.ts`. Never write a visible word straight into a component.
4. **Every element you may want to style has a stable name**: a class and a `data-ui="name"` attribute. Select by `[data-ui="plate-panel"]` and the name does not change when the layout does.

Tests keep these rules: `src/ui/noColourLiterals.test.ts` (rules 1 and 2), `src/i18n.test.ts` (rule 3) and `src/ui/uiStylingDoc.test.ts` (this page names every token the code uses).

## How to change a colour, a size or a font

- **A colour.** Open `src/styles/theme.css`, find the token, change its value, save. (A token the theme does not name yet is still in `:root` of `src/styles.css`; add it to the theme instead of editing the set underneath.) With `npm run dev` running, both the page and the open 3D scene recolour at once (see "How the 3D scene reads the tokens").
- **Make a state its own colour.** Many state tokens are aliases, for example `--tip-path: var(--success)`. Replace the alias with a colour and only that state changes.
- **A size.** Sizes are plain numbers in the rules of `src/styles.css` (`header { height: 56px }`, the three columns of `.workspace { grid-template-columns: 268px 1fr 300px }`, `font-size` in each rule). Corner radius and transition time are the tokens `--radius` and `--dur`.
- **A font.** The six stacks are tokens in `src/styles/theme.css` (see "The three text styles"). Only the two Latin faces are bundled; their files are declared in `src/fonts.css` (generated by `npm run fonts` from `scripts/gen-fonts-css.mjs`; do not edit it by hand).
- **An icon.** Replace its SVG file (see "Icons").
- **The batch-review viewer** (`dentalwork/batch-review/viewer.html`) has its own `tokens.css`; see "The batch-review viewer".

## The two themes

The app wears the **instrument theme** (`src/styles/theme.css`). Its shape comes from a small studio instrument: a light hardware body, white screens, dark ink, hairlines on a strict grid, plainly set words on the keys, machine numerals for every number, square plates with one small round on the keys, and nothing raised or shaded. Its colour comes from the owner's reference photograph of indigo-dyed peas in a steel pot: indigo ink, a teal accent, a soft turquoise for ranges, a cream note, and the single red speck in that photograph, which is the only red in the app and means alert.

Under it is the **paper theme** (`src/styles.css` on its own), which is kept only so the two can be compared.

- The theme is one attribute, `data-theme="instrument"` on `<html>`, set at start-up by `src/ui/theme.ts`.
- `?theme=paper` in the address shows any screen in the paper set; the choice is remembered in the browser. On the catalogue page (`kit.html`) the switch is the first dropdown in the header.
- The 3D view watches that attribute, so the DOM and the scene change colour together (see "How the 3D scene reads the tokens").

### The three text styles

Every word on screen is one of three things. A designer changes a size here, not in a component.

**1. Title** - the one large line that names a full screen ("What would you like to support?"). The **serif**, sentence case, never tracked, never uppercased, one per screen. Class `.title`. A screen's own heading is NOT this: it is `<ScreenHeading>` (`.screen-heading`), its own style, set out below.

**The size of a screen heading** is `--screen-heading-size`, `clamp(28px, 5.5vw, 76px)`: never below 28px,
never above 76px, and in between it follows the width of the window, so the line that names a screen is the
same weight of statement on a phone and on a studio display, in every language.

**2. Header** - four levels, all sans, every one set in the words as it is written, told apart by size and weight so a header never competes with the title above it or the sentence under it: `h1` the app, `h2` a screen or panel, `h3` a group, and the field and panel label (`.panel-widget-title`, `.dental-label`, `.brand small`).

**3. Content** - sans, sentence case: `p`, `li`, `label` and the small print (`small`, `.edit-note`).

**Two bundled faces, the Latin ones. Kana, kanji and Chinese characters come from the reader's own machine.**

Atkinson Hyperlegible Next leads every sans stack and draws every Latin word and every number - it is drawn for legibility, so 0 and O, 1 and l and I stay apart, which matters on a measurement. Noto Serif leads every serif stack and draws the title: it is the same family as the Noto Serif JP and Noto Serif TC behind it, so a title is one face in all three languages, and it is drawn at every weight, so a heavy title is a real bold rather than a browser smearing one weight sideways. Only its `latin` subset is bundled.

**Japanese is bundled too, but cut to size.** A CJK face is tens of megabytes, which is why this app used to
bundle none - and that left the Japanese title at whatever weight the reader's machine happened to have, or at
no weight at all on a machine with no Japanese serif installed. The Japanese here is a closed set, every word
of it in `src/locales/ja.ts`, so **Noto Serif JP** is subset to exactly those characters: 610 glyphs out of
some seventeen thousand, 115 kB a weight instead of 1.5 MB. It is the Japanese sibling of the Noto Serif that
draws the Latin, so the two languages are one family. Nothing downloads it unless a Japanese word is on screen,
and then only the weight that word is set in. Run `npm run fonts` after changing `ja.ts`;
`japaneseSubset.test.ts` fails if the two fall out of step.

Chinese is still the reader's own machine: `--font-title-zh` names the platform faces in order, and the
Traditional Chinese kanji forms differ from the Japanese ones, so the two must never share a face. These two are the part of the interface that is the same in every language, so they are bundled and look the same on every machine. Together they are about 100 KB.

No CJK face is bundled: every one worth having is tens of megabytes, and a clinic's machine already has a good one. Each stack names the platform faces in order instead - Japanese and Traditional Chinese separately, because their kanji forms differ, which is why **Chinese must never fall back to the Japanese face**.

| | sans (headers, content, numbers) | serif (the title) |
| --- | --- | --- |
| Latin, bundled | Atkinson Hyperlegible Next (400/500/700) | Noto Serif (400/800) |
| Japanese, from the system | Hiragino Sans, Yu Gothic UI, Yu Gothic, Meiryo, Noto Sans JP | Shippori Mincho B1, Hiragino Mincho ProN, Yu Mincho, Noto Serif JP |
| Traditional Chinese, from the system | PingFang TC, Microsoft JhengHei, Noto Sans TC | Noto Serif TC, Songti TC, PMingLiU |

`Shippori Mincho B1` leads the Japanese serif because it is the face the owner chose; a reader who has it installed gets it, and everyone else falls to the platform's own mincho.

### The docks (the 3D view's grid)

**The whole layout is `src/styles/layout.css`, and that file is the only place to change it.** Everything in it
reads from the tokens below, so a designer edits those and nothing else. Open it: each token says in plain words
what happens when you change it.

The dental steps lay their chrome out in a GRID across the 3D view: the step's title and the widgets in one
column, the control settings in another, the scene under all of it. Two boxes in different grid columns cannot
overlap - the browser will not allow it, whatever they hold, in any language, at any size. That is why the
layout is a grid and not a set of positions: before it, every panel carried coordinates of its own, so no panel
knew another existed and collisions were guaranteed.

Swapping the controls to the left side is two numbers (`--dock-controls-column: 1`, `--dock-title-column: 3`)
and no other change anywhere. Adding a column is one line (`--dock-columns`) plus the column number of whatever
goes in it. The walk's `u2b` check measures the real boxes on screen and fails if any two of them touch, so a
change that makes something collide is named rather than discovered later.

| Token | Value | What it sets | Where it shows |
| --- | --- | --- | --- |
| `--dock-gap` | `14px` | The space around and between the columns | Every panel's margin in the 3D view |
| `--dock-left` | `264px` | How wide the title-and-widgets column is | `.edit-badge`, `.viewport-object-status`, `.debug-section` |
| `--dock-right` | `300px` | How wide the controls column is | `.edit-bar`, `.edit-bar--orient`, `.dental-side` |
| `--dock-columns` | `var(--dock-left) minmax(0, 1fr) var(--dock-right)` | **The columns themselves.** Add one, drop one, reorder them; `1fr` is where the scene takes the room that is left | `.workspace--dental .viewport` |

### Waiting: the three types (`src/progress/`)

> The module and why it exists: **`src/progress/README.md`**. This section is the designer's half —
> where each type goes, what can be restyled, and what may not be.

There are **three kinds of waiting**, because there are three things an operator can do while it
happens: nothing, watch, or ignore. Every bar, spinner and loading word in the app is one of them.

| Type | Means | **Where it goes on screen** | Label | With no measure | Cancel |
| --- | --- | --- | --- | --- | --- |
| `blocking` | You cannot act yet | **Middle of the view**, over a veil that dims everything behind | Large, uppercase, above | 40px spinner in paper | Never |
| `step` | Your model is being worked on | **Top left of the 3D view**, under the step badge, over the scene | Small, above | 22px spinner | Never |
| `ledger` | These jobs exist | **Bottom left of the 3D view**, one row of the background-work list | Small, leading | Bar paces across | Where the job allows |

**Inheritance.** `PROGRESS_BASE` is what every type is before it is anything in particular — ink, a
spinner when it cannot count, label above, normal size, no veil. Each type then states only what it
**changes**, so the table reads as the differences between them rather than three full descriptions.

**To restyle one, edit its row in `src/progress/progressTypes.ts`** — `tone` (a token name), `waiting`
(`spinner` or `bar`), `labelPlacement` (`above` or `leading`), `size`, `veil`. Every instance of that
type moves with it, and the stylesheet draws those choices while making none of its own.

**What can be overridden, and what cannot.**

- **Colour and size cascade.** They reach CSS as the four custom properties above, declared on the
  type class, so any ancestor can set one and the instances inside follow — the same way a theme
  overrides `tokens.css`, without editing the table.
- **Structure does not.** Label placement, the veil, and whether waiting spins or paces are different
  markup, not different values. "This one blocks" is a statement about what the operator can do.
- **No call site overrides a type.** That is the hole this module closes: three surfaces drifted apart
  precisely because each styled its own waiting. A site chooses its *type*; the type decides the rest.

**The percentage is not a style option, and neither is the shape.** Both follow from one question:
does the job report a real fraction?

- **With a fraction** → a bar that fills, and the number beside it.
- **With none** → no number at all, and the type's `waiting` shape: a spinner that claims nothing, or
  a bar that paces across without filling.

A job that is one call into the core reports a start and an end and nothing between. A bar sitting at
a number nobody measured teaches a reader to stop believing the next one, so no type may ask for one.

**See them together in the style book:** `kit.html`, sections *Waiting 1 of 3 — blocking*, *2 of 3 —
step* and *3 of 3 — ledger*. Each group shows that type with a measure and without, and names where it
goes. They never appear together in the running app, which is why judging them used to mean loading a
model and catching each one as it went past.

**`data-ui` names:** `progress-blocking`, `progress-step`, `progress-ledger`.

## How the 3D scene reads the tokens

- One module reads them: `src/ui/tokenColour.ts`. `tokenColour('--name')` returns the computed value of the token as a number, `tokenCss('--name')` as `#rrggbb`. Outside a browser every colour is a neutral grey.
- `src/components/viewport/sceneColours.ts` names the token for every viewport colour (scene, model, support, marks). A component calls `useViewportColours()` and gets plain colours.
- **Live recolour.** `tokenColour.ts` keeps a revision number. It goes up when the root element's `style`, `class`, `data-theme` or `lang` attribute changes, when a `<style>` or `<link>` in `<head>` changes (a Vite hot update of `styles.css`), and when code calls `refreshTokenColours()` (a theme switch should call it). Components read it through `useTokenRevision()` (`src/ui/useTokenRevision.ts`), so they render again with the new colours; the tip markers' shared materials are recoloured on that render, and the support highlight repaints every vertex. No reload is needed.
- A rule edited by hand in the browser's devtools changes neither the attributes nor the head, so the page cannot see it. After such an edit run `mixoRefreshTokens()` in the console.
- Add a new 3D colour in three steps: a token in `:root`, one line in `sceneColours.ts` (or a `tokenColour('--name')` call), a row in the table above. The doc test fails if the row is missing.

## The two widgets every panel is built from

Every panel and every labelled control in the app is one of these two, so a designer styles them once and the
whole app follows. There is no second way to draw a group of controls or a labelled row: the `<details>` group,
`.field-row`, `.check`, `.number`, `.edit-size` and `.tool-option` of the older code are gone.

### Panel (`src/components/Panel.tsx`)

A titled block of controls. **Every panel has a title.** Four shapes, from two choices:

| | `collapsible` | `defaultOpen` / `open` |
| --- | --- | --- |
| A block that is always there | `false` (the default) | - |
| Opens and closes, starts open | `true` | `defaultOpen` (the default) |
| Opens and closes, starts closed | `true` | `defaultOpen={false}` |
| Opens and closes, the step remembers it | `true` | `open` + `onToggle` from the caller |

`columns={2}` or `{3}` lays the body out in that many columns of equal width. The panel is a CSS container, so a narrow panel drops its body to one column by itself - no window width, no media query.

`busy` dims the panel and marks it `aria-busy` while its contents are on their way (the supports check waiting for
a verdict). `className` is for where a panel sits, never for how it looks. The section names itself from its own
title (`aria-labelledby`), so the title words are the region's name and are never written twice.

The title is a solid bar with its words in the opposite colour, and a closed panel's bar is plainly lighter than an open one's (`--panel-title-bg` / `--panel-title-bg-closed`), so open and closed are told apart at a glance. Classes `.panel-widget`, `.panel-widget-title` (`.is-toggle` when it collapses), `.panel-widget-chevron`, `.panel-widget-body`. Names `{ui}`, `{ui}-title`, `{ui}-body`. (`.panel` is something else: the app's left and right side panels.)

### Field (`src/components/Field.tsx`)

One control with its label, and it holds whatever the control is: a text or number input, a slider, a checkbox, a segmented switch, a dropdown, or a value with nothing to change (`readOnly`, which makes it a plain row rather than a `<label>`).

- `layout="row"` (the default): label left, control right, on one line.
- `layout="stack"`: label on top. For a control that needs the width, or a label too long to sit beside one.
- A `row` field stands its label on top by itself inside a narrow panel, so the layout never has to be picked for a width.

- `grouped` for a control that is several controls (a segmented switch): the wrapper is a plain row too, since a
  `<label>` may only reach one control, and the group names itself with its own `aria-label`.
- `hint` is what the setting does, shown on hover; `className` is for where the field sits, never for how it looks.

The field styles whatever is inside it, so the control is bare: a slider, a checkbox, a `<select>`, an `<output>`
value and a unit `<small>` need no class of their own, and a typed value gets the underline and the right-aligned
tabular figures from `.field-control > input`. Do not put a control that draws its own label inside a field, or the
word appears twice - `NumberField` and `RangeField` **are** fields already, so use them directly.

Classes `.field`, `.field--row`, `.field--stack`, `.field--read-only`, `.field-label`, `.field-control`. Names `{ui}`, `{ui}-label`, `{ui}-control`.

All four panel shapes and a two-column panel holding every kind of control are on the catalogue page (`kit.html`).

## The bench (the scene with no mode) — `src/bench/`

**The step flow no longer ends here** (`FLOW_END`, `src/scenes/sceneMap.ts`): Step 3 writes its own
STL. The scene is otherwise unchanged and is still where Support Edit Mode, no-support zones, the
plate panel and the exports live, reached by *Any model* on the start screen or by opening a project.

Every step and mode in this app names itself in a badge. **The bench** is the one scene that does
not, because it is the app with nothing in hand: the plate, the panels, no tool, no step. It had no
name until `src/bench/benchScene.ts`; in code it is still `mode: 'off'`.

A designer needs it named because it is the scene an operator sees most, and because it is reached
three ways that all look identical — *Any model* on the start screen, Exit out of a mode, and opening
a saved project. There is no Step 4: the dental flow ends at its own export and does not come here.

Three rules hold the look of it, and `benchScene.test.ts` holds the app to them:

- **Nothing is dimmed.** Every other mode makes at least one panel section `inert` and posts a lock
  note saying why. The bench locks none, so no region wears the focus-mode dimming of §7.
- **The canvas carries no cursor of its own.** No tool ring, no brush circle: a press orbits.
- **No overlay belongs to it.** No badge, no mode bar, no veil. The **active object name** sits top
  left where a step would put its badge, and the view toggles take the top-right corner.

So restyling the bench means restyling the shell: header, the two panels, the viewport frame and the
footer, with the tokens above and nothing scene-specific. `src/bench/README.md` carries the region
table (what sits where) and the one open question — that arriving at the bench off the end of Step 3
announces nothing at all.

## Icons

Every icon is one SVG file in `src/ui/assets/icons/`, drawn by `src/ui/Icon.tsx` (`<Icon name="orient" />` finds `orient.svg`). To change an icon, replace its file; keep the file name, draw with `currentColor`, no fixed colour and no width or height on the root. The full list, where each appears and the rules for a replacement are in `src/ui/assets/icons/README.md`. `Icon` takes only a name and a class: size and colour come from CSS.

**The list of every icon is `src/ui/iconCatalogue.ts`, and the style book renders it** — `npm run dev` then
`/mixodental/kit.html`, or `npm run screens` for `.stitch/screens/icons.html`. Each card shows the icon at
its real size, resting and pressed, with the path of the file to edit. A prose table used to live in the
folder README and had already gone three icons out of date; `src/ui/iconCatalogue.test.ts` now fails when
the list and the folder disagree.

### Two sets, and the folder is the rule

| | `src/ui/assets/icons/` | `src/ui/assets/art/` |
| --- | --- | --- |
| Drawn by | `src/ui/Icon.tsx` | `src/ui/Art.tsx` |
| Colour | **one ink** — every fill and stroke becomes `currentColor`, so it takes the colour of the place it sits in and can never be off-palette | **its own**, kept exactly as drawn |
| Grid | 24, on a 240 artboard | 48, on a 480 artboard — a cell is ten units on both |
| Shown at | `--pixel-icon-inline`, 24px = **1x** | `--pixel-icon-key`, 144px = **3x** |
| Style | flat and front-on: at 1x a third dimension has nowhere to go | a picture of an object, with a keyline and a few tones |
| For | tool and cursor glyphs beside a word | the art on a choice key: an item type |

One ink is not a limitation for a glyph beside a word — it is the point, because it inverts with its key.
It is a limitation for a picture of an object: six rounds of drawing the three item types in a single
colour produced an archway every time, since the teeth, the keyline and the shading are the whole of what
makes a dental arch readable. Hence two components and two folders rather than a flag.

**A pixel-art file is shown at a whole multiple of its own grid or not at all.** At any other size each
fake pixel straddles a real one and the edges blur — which reads as a *badly drawn* icon when it is only a
badly *sized* one. The rail's icons sat at the shared `.tool-icon` 18px for a while: 0.75 of a CSS pixel
each, and no amount of redrawing would have fixed them. `src/ui/icons.test.ts` fails if either token stops
being a whole multiple of its own set's grid, and if any shape in a one-ink pixel file leaves the 24 grid;
`src/ui/art.test.ts` does the same for the 48 grid. 24px is also Material's standard icon size and the
WCAG 2.5.8 minimum target size, so the rule and the convention agree there.

**The finer grid is not a style choice.** Fourteen tooth cells need about 50 cells of arch perimeter and a
24 grid has about 27, so on 24 the teeth never fitted and every attempt collapsed into the one silhouette
that survives at that size: an archway. That, not the projection, is why the first isometric set failed.

**Some files are made by a script, and the FILE is still the source.** `tool-rim.svg`, `tool-area.svg`, `tool-supports.svg` and `cursor-rim.svg` are scaffolded by `scripts/pixel-icons.mjs`, which refuses to overwrite a file that exists (`--force` to mean it) and takes `--preview` to print a drawing as text without writing anything. The three item types in `assets/art/` are traced from the owner's reference by `scripts/trace-art.py`. Either way, replacing the file by hand is the supported way to change the picture.
