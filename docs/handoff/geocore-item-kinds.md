# Handoff to mixo-geocore: three more item kinds — dental model, night guard, retainer

**For:** `mixocreative/mixo-geocore` (vendored here at engine 63, commit `b5a71ab`).
**From:** mixoDental, 2026-11-11.
**Why:** the owner needs the app to offer **dental model**, **night guard** and **retainer** as item
types. The host cannot add any of them, and the three are not the same size of ask.

## Why the host cannot do this alone

```ts
// vendor/mixo-geocore/host/dental/dentalKind.ts
export type DentalKind = 'aligner' | 'denture';
```

A kind is not a label. It selects a **profile family** (`ALIGNER_PROFILES` / `DENTURE_PROFILES`) and,
behind it, a pipeline. And the profiles themselves are generated:

```ts
// host/dental/profileFiles.ts
// Generated by scripts/gen-profile-files.mjs from
// crates/geometry-core/src/dental/profiles/*.json: do not edit.
```

`crates/` is not vendored here — only `host/` and the built packages — so **neither a new kind nor a new
profile can be added from this repo.** The host's part is small and known: 13 files branch on the kind.

## The ask, in three parts of very different size

### 1. Night guard — probably one profile file

`alignerProfiles.ts` says it outright: *"Adding an aligner type is adding one file there: this list, the
card, the operator defaults and limits all follow, with no code change."*

A night guard is what an aligner is, mechanically: a thin shell, supported along its lower rim. It is
**thicker and unsegmented**, so it wants different numbers, not a different pipeline.

**What we need:** one `crates/geometry-core/src/dental/profiles/night-guard.json`, same schema as
`reference-aligner.json`, with values chosen by someone who knows the material. We deliberately have not
guessed: `ProfileDefaults` has eighteen fields — `outerSpacingMm`, `innerSpacingMm`, `maxSearchMm`,
`overhangAngleDeg`, `minTipSeparationMm` and the rest — and inventing a set would be fiction dressed as
data.

**Open question for you:** does a night guard's extra thickness change the rim detector's behaviour, or
only the support numbers? If the former, this is not just a profile.

### 2. Retainer — one profile, and one real question

Also a thin shell, so the same shape of answer. But a retainer has **a wire across the opening**, and
that is geometry the aligner pipeline has never met.

**The question we cannot answer from here:** what does rim detection do with the wire?

- Does the wire join the two sides into one loop, so the detected rim runs round the wire instead of the
  shell's trim edge?
- Do the clasps count as part of the shell?
- Should the wire be excluded from the support area, or does it need support of its own?

If the answer is "detection needs to know about the wire", this is a pipeline change, not a profile.
**Please answer this before quoting the work**, because it decides which of the two it is.

### 3. Dental model — a new kind, like `denture`

This one is genuinely different, and the reference sheet's own caption says why:
*"Solid · stable base / Low · base supports."*

- It is **not a shell**. There is no trim edge, so there is no rim to detect or draw.
- There is no "support area along each edge": supports go **under a flat base**.
- The whole Step 1 / Step 2 flow — rim, then the band along it — does not apply.

So it wants its own profile family and its own pipeline, exactly as `denture` has. That precedent is what
makes this a known quantity rather than research: `dentureProfiles.ts`, `DENTURE_PROFILES`,
`defaultProfileId`, `kindOfProfile` and `requireKind` already show the shape a third family takes.

**What we need:**
- `DentalKind` gains `'dental-model'`, and `DENTAL_KINDS`, `isDentalKind`, `defaultProfileId`,
  `profileIdsOf`, `kindOfProfile` and `requireKind` all follow.
- A `MODEL_PROFILES` family with at least one reference profile.
- A support strategy for a solid object on a base. Whether that reuses the denture path or needs its own
  is your call, not ours.

## What the host already has

The three icons are drawn and sitting unused, so nothing waits on art:
`src/ui/assets/art/dental-model.svg`, `retainer.svg`, `night-guard.svg`. The style book marks all three
**drawn, not wired up yet** so nobody draws a second set. `src/ui/iconCatalogue.ts` lists them.

## What we are NOT asking for

Not the other six kinds on the owner's reference sheet (surgical guide, crown & bridge, custom abutment,
wax-up, gingiva mask, bracket transfer tray, impression tray). They are drawn nowhere and wanted by
nobody yet. **An icon for a kind the pipeline cannot build is a promise the app does not keep**, and the
same goes for a profile nobody asked for.
